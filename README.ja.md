レンタルされたRunPod GPUで大規模モデルを実行します。保証として、モデルは決してローカルのGPUで実行されません。デスクトップアプリ、CLI、およびエージェント用のMCPサイドカーを、1つのRustライブラリとして提供します。

サイドカーは、エージェントが人間が設定した予算内で有料セッションを計画し、GPUをレンタルし、役割に基づいたタスクのキューを独立したランナーに渡すことを可能にします。ランナーはすべてのモデルスロットを稼働状態に保ち、失敗したチェックに対してのみ修正を行い、キューが空になるとポッドを停止します。監視プログラムは、他のすべての処理が完了した場合でも、計画の期限までにポッドを終了させます。

## ステータス

2026年10月2日と2026年10月3日に実証され、合計約5ドル。

- **Frontier:** 4 × RTX PRO 6000 (384 GB) で、Qwen3-Coder-480B (4ビットAWQ) を SGLang 上で実行。22分で準備完了後、31回のハンドオフを20秒で完了し、3.59ドル。
- **Swarmデータ:** 1つのロードされたモデルが、一度に数百のエージェントにサービスを提供します。480Bは、512エージェントで4,059トークン/秒に達し、1つのカード上の30Bは、256エージェントで10,147トークン/秒に達しました。
- **Runner:** 依存関係とレビューの再送を含むキューで、誰かが制御していなくても動作し、処理が完了するとポッドが停止します。
- **保証:** ローカルGPUは、すべての実行中にアイドル状態を維持します。

2026年10月7日以降、2つのプロジェクトが同時に使用しており、それぞれが独自の「レーン」で動作しています。aspire-siのトレーニングは`job`個のポッドで、ai-jam-sessionsの音楽レンダリングは`jam`個のポッドで行われます。

2026年10月11日、SGLangポッドが`Application startup complete`をログに記録し、その後、`/health`が7分間503エラーになりました。GPUは、約100Wでほぼ100%稼働し、`/v1/models`は200を返しました。その週に動作していたポッドは、CUDA 13.0でした。そのポッドはCUDA 13.2に配置されました。13.2が原因であることは示されていません。ピンを使用すると、プロファイルは動作したバージョンに留まります。このリリースでは、その問題を報告し、1つの完了で選択が返されるまで、レシピが準備完了とは見なされません。プロファイルは、ホストのCUDAバージョンを正確にピン留めすることもできます。

このリリースでは、レンタルされたポッドで実証されていません。1トークン準備チェック、`engine_unresponsive`と`engine_hung`のレポート、および`gpu.allowedCudaVersions`を送信する作成処理です。これらのパスは、偽のsshセッションと偽のRunPodに対するテストでカバーされています。それらを再確認するためにポッドは起動されませんでした。RunPodのドキュメントにあるv1`POST /pods`列挙型は、2026年10月11日に確認したところ、まだ13.0で停止します。13.1と13.2は、そのライターポッドが13.2に配置されたため、offrigのリストにあります。最小値は、まだ`gpu.minCudaVersion`のみを送信します。

構築およびテスト済みで、決定を待っています。ネットワークボリュームにFrontierのウェイトをステージングします。約21ドル/月（[ステージング](#ネットワークボリュームにステージングされたウェイト)を参照）。

次：最初の実際のフロンティアキュー。起動前に完全に計画されます。コードの引き渡しはコンパイルされ、ポッド上でテストされます。

## 機能

1つのウィンドウ（または1つのコマンド）から、offrigは次の処理を行います。

1. 現在のRunPod残高、GPUのリアルタイム価格、および残高がどのくらい持つかを表示します。
2. 指定されたティアのポッドを起動します。Ollamaでは1つの小規模なカードから、SGLangでは最大4つのRTX PRO 6000まで使用できます。そして、そのモデルをポッドに読み込みます。
3. ポッドへのSSHトンネルを開きます。
4. ポッドのモデルをZedに追加し、独自のプロバイダーとして設定します。
5. モデルがこのマシンで実行できないかどうかを7つのチェックで確認します。
6. ポッドを停止するか、すべてのGPUがアイドル状態になった後、一定期間後にポッドを終了します。

サイドカーを通じて、エージェントは予算に基づいてセッションを計画し、コンパクト化と再起動間でプロジェクトのメモリを保持し、監視なしでハンドオフキューを実行することもできます（[サイドカー](#サイドカーエージェント用)を参照）。

## 保証と、その保証がどのように維持されるか

- **モデルサーバーは、トンネルを通じてのみアクセスできます。** ポッドは、ピン留めされたエンジン、Ollama（`ollama/ollama:0.35.0`）またはSGLang（`lmsysorg/sglang:v0.5.20-cu130`）を実行し、ポッド自身のループバックにバインドされ、ポッドは`22/tcp`のみを公開します。見つけて悪用できるパブリックHTTPエンドポイントはありません。レシピは、エンジンをループバックから移動させることができません。
- **Zedは、独自のポートでトンネルと通信します。** トンネルは`127.0.0.1:11435`でリッスンします。ローカルのOllamaは`11434`にあります。offrigは、トンネルを`11434`に配置することを拒否するため、切断されたトンネルがローカルサーバーに到達することはありません。代わりに、リクエストは失敗します。
- **Zedは、プロバイダーを切り替えません。** ポッドのモデルは、Zed内の別の`offrig`プロバイダーです。ポッドがダウンしている場合、それらのいずれかを選択するとエラーが発生します。Zedは、別のプロバイダーを試行しません。
- **ウェイトはローカルに存在しません。** モデルは、ポッドによってポッドにプルされます（またはHugging Faceからダウンロードされるか、ステージングされたネットワークボリュームから読み込まれます）。

ガードは、offrigが観測できる事実に基づいて、毎回これを検証します。

| チェック | 失敗する場合 |
|---|---|
| トンネルはローカルのOllamaポートを回避します | トンネルポートは11434です |
| Zedはトンネルを通じてポッドモデルを送信します | ZedのプロバイダーURLは、トンネル以外のURLです |
| ポッドのOllamaはインターネットに公開されていません | ポッドはポート11434を公開します |
| トンネルはポッドで終了します | トンネル経由のモデルリストは、SSH経由でポッド上で読み込まれたリストと異なります |
| ポッドモデルはこのマシンにありません | ポッドモデルはローカルのOllamaにも存在します |
| ポッドモデルとローカルのZedモデルで名前が同じものは存在しません | offrigプロバイダーの1つの名前が、ZedのローカルOllamaリストにも含まれています |
| Zedが提供するすべてのモデルは、ポッドに存在します | Zedは、ポッドに存在しないモデルを提供します |

## インストール

WindowsとOpenSSH（組み込み）、およびモデルをエディターで使用する場合はZed、およびRunPodアカウントが必要です。

1. `offrig-<version>-windows-x64.zip` を [リリース](https://github.com/mcp-tool-shop-org/offrig/releases) からダウンロードし、リリースの `SHA256SUMS` と照合して、`PATH` に解凍します。これには、`offrig.exe` (CLI)、`offrig-app.exe` (アプリ)、および `offrig-mcp.exe` (サイドカー) が含まれます。
ソースコードからビルドする場合は、次のコマンドを実行します: `cargo build --release`。Rust 1.98.1 を使用します (`rust-toolchain.toml` で固定)。
2. RunPod API キーをユーザー環境変数 `RUNPOD_API_KEY` に設定します。
3. SSH 公開キーを RunPod のアカウント設定に追加します。offrig は、利用可能な場合は `~/.ssh/runpod_rustline`、そうでない場合は `~/.ssh/id_ed25519` を使用します。
4. エージェントの場合、サイドカーをユーザーレベルで Claude Code に登録します: `claude mcp add --scope user offrig -- <path>\offrig-mcp.exe`。これにより、プロジェクトのストアが初回使用時にのみ開かれるため、使用しないプロジェクトでは問題ありません。

[ハンドブック](https://mcp-tool-shop-org.github.io/offrig/handbook/) には、最初のポッド、サイドカー、構成、レーン、およびジョブポッドに関する手順が記載されています。

## 使用方法

**アプリ:** `offrig-app` を起動し、プロファイルを選択し、[ポッドの起動] を押します。準備が整うと、モデルが Zed のエージェントパネルに「RunPod · …」として表示されます。最初の起動後、Zed を 1 回再起動して、`OFFRIG_API_KEY` を認識させます。

**CLI:**

```text
offrig status                 balance, runway, pods
offrig gpus --count 2         live offers for a GPU count
offrig profiles               tiers and their models
offrig up medium              launch, pull, wire Zed, run the checks, hold the tunnel
offrig up frontier --wait 180  wait up to 3 hours for the GPUs, renting nothing meanwhile
offrig tunnel medium          hold the tunnel to a running pod
offrig check gpt-oss:120b     streamed chat with a tool call, the way Zed sends it
offrig guard                  run the seven checks
offrig pull <model>           pull another model onto the pod
offrig connect                open the pod's /workspace in Zed for remote editing
offrig down medium --yes      terminate the pod
offrig zed-remove             take the provider out of Zed
offrig budget 15              set this project's spending cap for agent sessions (human only)
offrig index src docs           index this project for hybrid search (CPU embeddings)
offrig verify calibrate gold.jsonl --model gemma4:31b   score a local verifier model
offrig stage frontier --dc EUR-IS-1 --yes   stage weights on a network volume (bills monthly)
```

`offrig --help` と `offrig <command> --help` には、すべてのコマンドとフラグがリストされています。上記のブロックは、毎日の設定です。`offrig init`、`offrig models`、`offrig zed`、および `offrig up --no-zed` は、[ハンドブック](https://mcp-tool-shop-org.github.io/offrig/handbook/usage/) に記載されています。

### 出力、終了コード、およびエラー

- **ログレベル:** `-q` は、エラーとコマンド自体の結果のみを出力します。`-v` は、各 RunPod 呼び出しとそのタイミングを追加します。`--debug` は、失敗したレスポンスの本文と完全なエラーチェーンを追加します。
API キーは、すべてのレベルでマスクされます。
- **終了コード:** `0` は成功、`1` は修正が必要な問題 (引数、構成、ガードまたは予算の拒否、キーの欠落)、`2` は実行時のエラー (RunPod、ネットワーク、ssh、タイムアウト、容量不足) を示します。
- **サイドカーエラー** は結果であり、プロトコルエラーではありません: `ok:false` (安定した `code`)、`error` テキスト、`next_action`、および `retryable`。コードは、[ハンドブックのリファレンス](https://mcp-tool-shop-org.github.io/offrig/handbook/reference/) にリストされています。

## サイドカー（エージェント用）

`offrig-mcp`は、Claude Codeなどのエージェントが使用するMCPサーバーです。各プロジェクトごとにデータベースを`<project>/.offrig/offrig.db`に保持し、すべてのポッドよりも長く存続するため、セッションは圧縮または再起動後も、情報を再説明することなく維持されます。

| ツール | 機能 |
|---|---|
| `offrig_status` | プロジェクト、予算、RunPod の残高と猶予期間、offrig のポッド、各オープンプランとその `plan_id`、レーン名、およびポッド名、保留中の作業がフラグ付けされたハンドオフキュー。各ポッドには、RunPod レコードから取得した `gpu_count` と `gpus` (`2x <type>`) に加えて、プランの `planned_gpu_count` が含まれます。 |
| `offrig_offers` | GPU数のためのライブGPUの提供 |
| `offrig_plan` | 最悪の場合 (ライブ価格 x (最大時間 + 780 秒の自動停止時間)、小数点以下切り上げ) でセッションの価格を設定し、残りの予算を超えた場合は拒否します。応答には、レーンの `ssh_alias` と起動によって作成される `pod_name`、および要求される `container_disk_gb` (オプションの `container_disk_gb` はプロファイルのものをオーバーライドします。「コンテナディスク」を参照) が含まれます。オプションの `max_price_hr` と `no_fallback` は、レンタルできる GPU を制限します (「プランのハードウェアを固定する」を参照)。オプションの `wait_minutes` は、容量がない場合に起動が再試行する回数を設定します (「容量を待つ」を参照)。 |
| `offrig_memory_search` | アクティブなプロジェクトメモリを検索し、各結果にソースと日付を含めます |
| `offrig_memory_record` | 簡単な説明、制約、決定、事実、またはチェックポイントを追加します。変更は、理由とともに以前のものを上書きします |
| `offrig_handoffs` | 役割に基づいたタスクのキュー（それぞれに受け入れチェックが必要であり、オプションで決定的なチェックも可能）、それらのリスト表示、役割ブロックのプレビュー、タスクの最良の出力の表示（これも`.offrig/out/`に書き込まれます）、結果の記録（完了、無効、違反、失敗、フィードバック付きでの再試行） |
| `offrig_launch` | **実行します。** `plan_id`のみを受け入れます。最悪の場合をコミットし、GPUのレンタルを待機し、ポッドを起動し、トンネルを開き、モデルをプルし、監視プログラムを開始します。計画ごとにべき等です。レーンにすでにアクティブな計画またはポッドがある場合は拒否されます：`lane <tag> has a live pod <name> (plan <id>); shut it down first` |
| `offrig_job` | 起動の進行状況 (ポッドが起動している間、ステップは呼び出し時のポッドの状態から派生し、`progress.pod_status` は生の v2 ステータスです。各容量の再試行は `progress.capacity_wait` にカウントされます)。GPU の種類、`gpu_count`、`gpus`、`planned_gpu_count`、および ssh が起動したら `measured_gpu_count` (カードがない場合の読み取り値は `0` です)。`gpu_mismatch` は、レコードまたは測定値がプランと異なる場合に true になります。ホストの CUDA バージョンは `nvidia-smi` で測定され、ホストがプランの CUDA 最小値よりも古い場合は、大きな `warnings` エントリが出力されます。レシピの場合、`ready` は 1 つの完了で選択肢が返されたことを意味します。`engine_hung` と `engine_unresponsive` は、ポッドを起動したままにします。監視プログラムの稼働状況、残り時間、これまでの消費量 |
| `offrig_ask` | ポッドモデル上のタスクを1回実行し、プロジェクトストアからコンテキストを構築します。応答は信頼できない出力として返されます |
| `offrig_run` | すべてのモデルスロットを稼働状態に保つ独立したランナーを開始します。各準備完了のタスクをドラフトし、失敗したチェックに対して最大2回修正し、結果を依存するタスクにフィードし、キューが空になるとポッドを停止します（ただし、`keep_pod`の場合を除く）。コードでチェックできない作業は、レビュー待ちで保留されます |
| `offrig_put` | ローカルファイルまたはディレクトリをジョブポッドにコピーします（scp）。相対ポッドパスは`/workspace/job`の下にあります。オプションの`plan_id`（下記参照） |
| `offrig_exec` | ジョブポッドでbashコマンドを実行し、サイドカーよりも長く実行されるように独立して実行します（`start`）。実行中または終了したことを報告し、終了コードとログの末尾を含めます（`status`。`save_log`はログ全体をローカルファイルにもコピーします）、それを終了します（`stop`）、または短いコマンドを今すぐ実行し、stdout、stderr、および終了コードを返します（`run`、`timeout_secs`デフォルトは30、最大120）。オプションの`plan_id`（下記参照） |
| `offrig_get` | ジョブポッドからファイルまたはディレクトリをコピーし、不足しているローカルの親フォルダーを作成します。ポッドのディスクが削除される前に実行します。オプションの`plan_id`（下記参照） |
| `offrig_shutdown` | **ポッドを破棄します。** 終了し、計画の会計を測定された使用量で閉じます。タスクが実行中の場合は、理由が与えられない限り拒否されます。レーン自体の`~/.ssh/config`ブロックを、そのポッドの名前がレーンのポッドである場合に削除します（`ssh_block_removed`） |
| `offrig_complete` | **消費します。** 許可されたプロジェクトとモデルに対してのみ、1 つの OpenRouter チャット完了を実行します。予算に対して最悪の場合をコミットし、回答をプロジェクトファイルに書き込みます (すでにそのパスがある場合は、そのパスを置き換えます)。実際の料金を記録します。 |

**ジョブツールが作用するジョブプラン。** `offrig_put`、`offrig_exec`、および`offrig_get`は、オプションの`plan_id`を受け入れます。1つのアクティブなジョブプランがあり、`plan_id`がない場合、以前と同様にそれを使用します。1つ以上のアクティブなジョブプランがあり、`plan_id`がない場合、拒否し、アクティブなプラン（ID、プロファイル、ポッド名）をリスト表示します。推測はしません。`plan_id`がある場合、そのプランのポッドに対してのみ作用し、ポッドの名前がそのプランが所有するものであることを確認した後でのみ作用します（別のレーンのポッドは拒否され、単に別のレーンであるというだけではありません）。すべてのジョブツールの応答と`offrig_job`は、作用した`project`と`plan_id`を示します（ジョブツールの応答には`lane`も含まれます）。`offrig_status`は、`project`を示し、各アクティブなプランとその`plan_id`、レーン、およびポッド名をリスト表示します。

**タスクとスキル。** MCP Tasks に対応したクライアントは `offrig_launch` をタスクとして実行できます。`tasks/get` は `offrig_job` と同じ状態を示し、`tasks/cancel` は進行中の起動を（`offrig_shutdown` を通じて）取り消します。準備済みのセッションを止めるには `offrig_shutdown` を呼び出してください。ポッドをいつ停止するかは、引き続きプランの期限とウォッチドッグが決めます。サーバーは手順スキル `offrig-session` も 1 つ公開しています。詳しくは [side-car ハンドブック](https://mcp-tool-shop-org.github.io/offrig/handbook/side-car/#tasks) を参照してください。

役割は、Role OS（ドキュメントとスターターパックカード）と、Role OSの形式でここに同梱されている4つのゲーム役割（ゲームデザイナー、システムデザイナー、ナラティブデザイナー、ロアキーパー）から取得されます。予算の上限は、人間が設定します。

```text
offrig budget --provider runpod 30       RunPod's cap (run in the project directory)
offrig budget --provider openrouter 8    OpenRouter's cap
offrig budget --show                     every cap, beside each provider's own balance
```

すべてのサイドカーの起動は、**ウォッチドッグ**を開始します。これは、エージェント、セッション、またはサイドカーが存在しなくても、計画の期限（コミットされた時間 + 最大時間）でポッドを終了する別のプロセスです。失敗した検索に対しては何も実行せず、正確に1回だけ終了し、処理を完了し、`.offrig/watchdog-<plan>.log`にログを記録します。エンジンがサービスを開始する前に、レンタルされたポッドの準備が失敗した場合、サイドカーはポッドを課金対象として残すのではなく、それを終了させます。
`engine_hung`と`engine_unresponsive`は、すべてのコンポーネント（サイドカー、CLI、アプリ）に対して、レポート専用です。サイドカー、CLI、アプリはポッドを起動したままにし、「準備完了」と表示しません。CLIとアプリでは、コマンドはエラーで停止します。サイドカーでは、起動結果は成功した状態のままになるため、ポッドは削除されず、計画はコミットされた状態のままになり、ジョブは`running`のままになります。すでに終了したエンジンプロセスは、レポートの対象ではありません。サイドカーでは、これは失敗した起動であり、補償メカニズムがポッドを削除します。`offrig up`またはアプリで起動されたポッドには、ウォッチドッグは存在しません。コマンドがエラーで停止した場合（ハング、応答しないエンジン、終了したエンジン、またはタイムアウト）、ポッドは`offrig down <profile> --yes` or the app's Shut down. A pod RunPod reports as `ERROR` or `EXITED`という例外が発生するまで、課金対象のままになります。この例外が発生した場合、すべてのコンポーネントでポッドが終了します。

設計とその証拠は、[docs/sidecar-design.md](docs/sidecar-design.md)にあります。

### レーン：プロジェクトごとに1つのサイドカー、競合なし

2つのプロジェクトは、1つのRunPodアカウントで同時にサイドカーを実行できます。各プロジェクトは、他のプロジェクトが共有しない独自の**レーン**（SSHエイリアス、トンネルポート、ポッド名タグ）を取得します。

| | プレーンレーン（CLI、アプリ、Zed） | プロジェクトのレーン |
|---|---|---|
| SSHエイリアス | `offrig` | `offrig-<tag>` |
| トンネルポート | `11435`（ランナー`11436`） | 最初に`11500`、`11502`、...が使用可能になります（ランナー：上記のポート） |
| サイドカーポート（シェルドライバー） | なし | `11700` + レーンの割り当て：`11700`、`11701`、... |
| ポッド名 | `offrig-<profile>` | `offrig-<tag>-<profile>` |
| SSHブロック | `# >>> offrig:offrig >>>` | `# >>> offrig:offrig-<tag> >>>` |

`<tag>`は、プロジェクトフォルダーの名前（`aspire-si`、`ai-jam-sessions`）から取得され、2つのプロジェクトが同じフォルダー名を使用する場合、短いハッシュが追加されます。プロジェクトのレーンは、最初にセッションを計画したときに割り当てられ、offrigの構成ディレクトリ内の`lanes.toml`に書き込まれ、保持されます。同じプロジェクトは、再起動後も同じレーンを使用します。割り当てにはロックファイルが使用され、レジストリはアトミックに書き込まれるため、同時に起動する2つのサイドカーが同じタグ、エイリアス、またはポートを共有することはありません。どのレーンも`11434`（ローカルOllamaのポート）にすることはできません。範囲は`11500`から始まり、それ以外を指定するように編集されたレジストリは拒否されます。計画は、自身のレーンを記録し、起動、ランナー、ウォッチドッグ、およびシャットダウンはすべて、グローバル構成ではなく、そのレーンを使用します。

サイドカーは、常に自身のレーンに名前が付けられたポッドとのみ一致、リスト、または停止します。別のプロジェクトのレーン、プレーンレーンの`offrig-<profile>`ポッド、およびアカウント上の他のすべてのポッドはそのままにします。ライブポッドの存在を確認する起動チェックは、自身のレーンのみを対象とし、シャットダウンは、ポッド名が計画のレーンと一致しない場合にポッドを拒否し、トンネルの孤立チェックは、フォワードとエイリアスがレーンのものである場合にのみ、古い`ssh`を停止します。レーンが存在する前に作成された計画は、レーンを記録しておらず、プレーンレーンで実行され続けるため、古いスキームで起動されたポッドは、起動したのと同じ計画によってシャットダウンされます。

**サイドカー自身のポート。** `offrig-mcp`は、stdio経由でMCPと通信します。セッション全体にわたって1つの接続を開いたままにするシェルドライバー（セッション自身のMCP接続が不安定な場合）は、それをループバックHTTPポートの背後に配置し、そのポートは以前はマシン全体で1つの番号でした（`11439`）。2番目のプロジェクトのドライバー、または他のプログラムがそれを取得すると、最初のサイドカーは何も言わずに停止しました。現在は、プロジェクトごとにデフォルト設定されており、トンネルポートと同様に、プロジェクトのレーンから取得されます。レーンスロット`i`（トンネルポート`11500 + 2i`）は、サイドカーポート`11700 + i`を取得します。
範囲`11700`から`11763`は、レーンが持つことができるすべてのトンネルポートとランナーポート（`11500`から`11627`）、プレーンレーンの`11435`と`11436`、およびローカルOllamaの`11434`よりも上にあります。したがって、サイドカーポートはトンネルポートになることはありません。新しいものは保存されません。`lanes.toml`は変更されておらず、ポートはレーンから派生します。`OFFRIG_SIDECAR_PORT`は引き続きそれをオーバーライドします。ポートではない値、1024未満の値、または`11434`、`11435`、`11436`、またはレーントンネル範囲内の値は拒否されます。

```
offrig-mcp --sidecar-port --project <dir>           # print the port; allocates the lane if the project has none
offrig-mcp --sidecar-port --check --project <dir>   # also exit 1 if something already holds it
```

`--check`を使用すると、使用中のポートはエラーとなり、ポート名が表示されます。また、オフリグのサイドカーがそのポートに応答した場合、そのサイドカーがサービスを提供しているプロジェクトのパスが表示されます。「サイドカーポート11700は使用中です。オフリグのサイドカーがすでにそのパスのプロジェクトをサービスしています。まずそれを停止するか、OFFRIG_SIDECAR_PORTを未使用のポートに設定してください」。このチェックは、ドライバーがすでにどのように応答しているかを確認します（どのプロジェクトもサービスしていないリクエストであり、ドライバーはどのツールにもアクセスする前にそれを拒否します）。したがって、実行中のサイドカーには何も影響しません。`offrig_status`は、レーンの`sidecar_port`を報告します。

**1つのレーンに1つのアクティブなポッドを配置。** 1つのレーンには1つのSSHエイリアスと1つのトンネルポートがあるため、一度に1つのポッドにしか対応できません。レーン内の2番目のポッド（`offrig-<tag>-jam`の隣の`offrig-<tag>-job`）は、エイリアスを自分自身に再設定し、最初のプランの`offrig_put`、`offrig_exec`、および`offrig_get`を誤ったマシンに送信します。したがって、レーンに開いているプランや、レーンが所有するアクティブなポッドがある場合、`offrig_launch`は拒否します。`lane <tag> has a live pod <name> (plan <id>); shut it down first`, before anything is committed or rented. The plain lane's `offrig up`
アプリも同様に、別のプロファイルのポッドに対して拒否します（同じプロファイルのポッドは引き続き再利用されます）。最初に最初のプランを停止し、次に次のプランを開始します。

### リソースの空きを待機中

`no_fallback`または`max_price_hr`で制限されたプランは、リソースが不足することが多いため、起動は失敗する代わりに、何もレンタルせずに静かに再試行します。待機時間は、次の順序で決定されます。プランの`wait_minutes`（プランに保存されている`offrig_plan`引数。`0`は即座に失敗します）、またはプロファイルの`wait_for_gpu_minutes`です。`job`プロファイルはデフォルトで20分です。待機時間は、プランの残りの時間から5分の予約時間を差し引いた時間まで短縮されるため、プランの期限を過ぎることはありません。また、待機中は何もレンタルされないため、コミットされた最悪のケースには影響しません。`offrig_launch`は`capacity_wait_minutes`を報告します。待機中は、`offrig_job`に`progress.capacity_wait`（`checks`、`waited_secs`、`limit_secs`）と、どのチェックであるかを示すステップが表示されます。待機時間が終了すると、起動は`no capacity`で失敗し、何もレンタルされません。

### プランのハードウェアを固定する

プロファイルには、GPUの種類が優先順にリストされており、RunPodは、利用可能な最初のGPUを選択します。そのため、制限がない場合、プランは、メモリ容量が少なく、古いドライバーを使用し、価格が異なるGPUに割り当てられる可能性があります。3つの制限により、プランが使用できるハードウェアに割り当てが制限されます。プランニング自体は引き続き無料ですが、制限は、プランが利用できるリソースを絞り込むだけです。

| 制限 | 場所 | 効果 |
|---|---|---|
| `min_cuda` | プロファイル（`config.toml`） | 最も古いホスト CUDA（ドライバー）バージョンは、RunPodのリスト（`13.2`、`13.1`、`13.0`、`12.9`、…`11.8`）から取得されます。ポッドの作成時に、このバージョンが`gpu.minCudaVersion`として送信されるため、コピーされた最新バージョンよりも新しいホストも条件を満たします。カタログがGPUに対して`cudaVersions`を返した場合、プランはそのタイプを維持するのは、このバージョン以上のバージョンが存在する場合のみです。カタログがリストを省略した場合、コピーされたリストが代替として使用されます。ジョブプロファイルでは、このバージョンとイメージ自身の`[profiles.job] min_cuda`のうち、新しい方が適用されます。 |
| `min_vram_gb` | プロファイル | プランが受け入れる最小の合計VRAM（プロファイル内のすべてのGPUの合計）。それ以下の値を持つプランは破棄され、メモリ容量が指定されていないタイプRunPodのプランも破棄されます。 |
| `max_price_hr` | `offrig_plan`引数 | ポッドにかかる可能性のある最大のコスト（すべてのGPUの合計$/時間。この数値は`offrig_offers`に表示されます）。これを超えるオファーは拒否され、現在価格がリストされていないタイプも同様です（上限に準拠することはできません）。 |
| `no_fallback` | `offrig_plan`引数 | プロファイルで許可されるのは、最初のGPUファミリーのみです。2つのRTX PRO 6000 Blackwellエディション（サーバー版とワークステーション版）は、1つのファミリーに分類されます。それ以外のカード（A100 SXMやPCIeなど）は、それぞれ別のファミリーに分類されます。 |

プロファイルフィールドはオプションであり、デフォルトでは設定されていません。したがって、以前のオフリグによって記述された`config.toml`は、変更せずにロードされます。`job`プロファイルは`min_cuda = "13.0"`を設定します。

`cuda_versions`は、例えば`min_cuda`の横に配置されるオプションの厳密なリストです。
`cuda_versions = ["13.0"]`。設定されると、ポッド作成プロセスは、そのリストを次のように送信します。
`gpu.allowedCudaVersions`は、記述された順に処理され、また、別のフロアには送信されません。
`offrig_plan`はリストを表示します。これを`min_cuda`とともに設定することで、ジョブを含めた一連の処理を実行できます。
画像自体が床面を表している場合、それは却下される。両方を組み合わせると曖昧になる。それぞれのバージョンは、それぞれが独立して解釈できるようにする必要がある。
オフリッグというものが1つだけ受け入れられます。そのリストは、最新のものから順に並んでおり、13.2、13.1、13.0、そして12.9と続きます。
11.8、13.2、および13.1は、RunPodでドキュメント化されているv1列挙型よりも進んでいます（参照日：2026年10月11日）。
13.0で停止します。これらは、2026年10月11日に設置されたライターポッドが配置されたため、リストに記載されています。
13.2 ホスト。フロアからは依然として`gpu.minCudaVersion`しか送信されません。

`offrig_plan`は、残りのリソースから最悪のケースを算出し、価格を設定します。
`(max_hours + 780 s) x min(max_price_hr, the dearest listed price among the remaining GPUs)`（小数点以下を切り上げてセント単位で表示。780秒は、オンポッドの自己停止マージンである120秒に、660秒の再試行時間を加えたものです）。これがない場合、
`max_price_hr`は、以前と同様に、プロファイルに記載されている最も高い価格となります。残りのリソースが何もないプランは、すべてのGPUでエラーが発生した場合の理由とともに拒否され、何も記録されません。

プランは残った GPU リストと、CUDA の下限または正確な CUDA リストのいずれかを保存し、
`offrig_launch` はプランが保存したものからのみレンタルし、後からプロファイルを編集しても使いません。`offrig_job` とサイドカーの起動結果は、
実際にレンタルした GPU の種類とホストの CUDA バージョンを `rented` オブジェクトで報告します。
ポッド API はホストの CUDA バージョンを報告しないため、ssh が上がると起動処理はレーン経由で
`nvidia-smi` を 1 回実行し、ヘッダー（`CUDA Version: 12.8`、新しいドライバーでは
`CUDA UMD Version: 13.4`）から読み取ります。`rented.cuda_source` は `nvidia-smi` か
`pod API` を示します。ホストの CUDA がプランの下限より古い場合、GPU が
プランに含まれないものだった場合、または価格がプランを上回る場合、`offrig_job` は `warnings`
の項目を返し、`next_action` を `WARNING` で始めます。自動では何も終了しません。レンタルを止めるかどうかは
呼び出し側の判断です（`offrig_shutdown`）。ポッド API も `nvidia-smi` も CUDA バージョンを返さない場合は、
`rented.notes` にそう記され、下限は未確認のままです。

### コンテナディスク

ポッドには、ホストにローカルなコンテナディスクと、`/workspace`にマウントされたボリュームという2つのディスクがあります。一部のホストでは、`/workspace`は速度の遅いネットワークファイルシステムです。あるジョブポッドでは、そこで32MB/s、コンテナディスクでは354MB/sという測定値が得られました。また、約130GBのモデルを時間内に取得できませんでしたが、コンテナディスクはわずか60GBでした。コンテナディスクのサイズは、プロファイルの`container_disk_gb`（組み込みプロファイルでは30〜60GB。`job`プロファイルは60GB）であり、ポッドの作成時に`disk`として渡されます。`offrig_plan`は`container_disk_gb`（1〜2000）を受け取り、それを使用して1つのプランをオーバーライドします。プランはそれを保存し、起動はそれを送信し、プランの応答と`offrig_status`は、実際に使用されているサイズを表示します。

- コンテナディスクは**料金が発生しません**。offrigはGPU時間のみを料金としており、そのためプランの最悪のケースは、どのサイズでも同じです。RunPodはディスクの料金を請求します。ポッド（`offrig_job`に表示）に対して報告される料金にコンテナディスクが含まれているかどうかは、ここでは確認されていません。
- offrigは、ダウンロードしたファイルを自動的に移動しません。ジョブコマンドは、`/workspace`ボリューム（`/workspace/hf`）上で`HF_HOME`から開始されます。コンテナディスクを使用するには、コマンド内で独自の（`HF_HOME=/root/hf python ...`）を設定します。
- コンテナディスクは、ネットワークボリュームのないボリュームと同様に、ポッドとともに削除されます。結果を`offrig_get`を使用して事前にコピーしてから、`offrig_shutdown`を実行してください。
- 1から2000までの制限は、offrig独自のタイプミスに対する安全策です。RunPodの実際の制限は確認されていません。

### ジョブポッド

`job`を持つプロファイルは、モデルの提供ではなく、トレーニング実行などのタスクを実行するためにGPUをレンタルします。そのポッドは、固定されたPyTorchイメージ（`runpod/pytorch:2.8.0-py3.11-cuda12.8.1-cudnn-devel-ubuntu22.04`、Blackwell用のCUDA 12.8）をsshdとそれ以外に何も含まずで実行します。

- モデルは使用されないため、トンネルはなく、Zedに何も接続されていません。sshdは一切の転送を許可しません（`AllowTcpForwarding=no`）。アクセスできる唯一の方法は、ポッドにsshで接続することです。
- ジョブプロファイルにはモデルがリストされておらず、レシピも含まれていません。設定チェックで拒否されます。
- `offrig up`とアプリケーションは、何かをレンタルする前にジョブプロファイルを拒否します。処理は、サイドカーを通じて行われます：`offrig_plan profile=job`、`offrig_launch`、次に`offrig_put`、`offrig_exec`、そして`offrig_get`。sshdが応答すると、起動の準備が整います。
- コマンドは、ポッド（`setsid nohup`）内の`/workspace/job`で独立して実行されるため、サイドカーやsshセッションよりも長く存続します。これはbase64として送信されるため、sshシェルによって内容は読み込まれません。ログと終了ステータスは`/workspace/offrig/jobs/`に保存されます。Hugging Faceからのダウンロードは、ポッドボリュームの`/workspace/hf`に保存されます。
- `offrig_exec action=run`は、実際の作業ではなく、簡単なチェック（`ls`、`nvidia-smi`）に使用されます。コマンドは、`timeout`（デフォルトは30秒、最大120秒）の下で完了まで実行され、`stdout`、`stderr`、`exit_code`、および`timed_out`が返されます。出力は、各ストリームの最後の64KBに切り捨てられ（`truncated`）、信頼できないポッド出力となります。より長い時間が必要なコマンドは、`start`です。
- ジョブのログの末尾には、進行状況バーが折りたたまれて表示されます。tqdmスタイルの再描画は、キャリッジリターンによって結合され、最後のフレームのみが表示されます。`offrig_exec action=status save_log=<local path>`は、ジョブのログ全体を、書き込まれたとおりにローカルファイル（親フォルダーが作成されます）にコピーするため、ログの末尾を短く保つことができます。
- イメージはCUDA 12.8でビルドされているため、ジョブプロファイルには、実行される最も古いホストのCUDAバージョン（`min_cuda = "12.8"`）が記述され、その値が`gpu.minCudaVersion`としてポッドに設定されます。そうしないと、古いドライバーを持つホストがポッドを開始し、レンタルが開始された後にtorchがGPUを見つけられません。実際の作業では、イメージよりも多くのリソースが必要になる場合があります。`job`プロファイルは、プロファイルに`min_cuda = "13.0"`も設定します（上記を参照）。これは、実行するジョブが現在のvLLMをインストールし、そのPyTorchがCUDA 13ビルドであるためです。
- 予算、計画、監視、およびシャットダウンは、他のプロファイルと同様に機能します。`offrig_shutdown`の前に結果をコピーします。ポッドのディスクも一緒に削除されます。
- `jam`は、ai-jam-sessionsジョブプロファイルが歌をレンダリングするために使用するものです。SoulX-Singerは、トレーニングカードよりもはるかに少ないリソースを必要とするため、安価な24〜48GBのものをレンタルします。セットアップとセッションは、そのリポジトリ（`docs/vocal-offrig.md`）に保存されます。offrigは、歌について何も知りません。

### ネットワークボリュームにステージングされたウェイト

レシピプロファイルは、起動時に毎回ウェイトをダウンロードします。以前のバージョンでは、準備完了までに約20/22分かかりました（252 GB、$8.36/時間）。ステージングでは、ウェイトを1回だけRunPodネットワークボリュームに配置します。

```text
offrig stage frontier --dc EUR-IS-1          shows the monthly cost, changes nothing
offrig stage frontier --dc EUR-IS-1 --yes    creates the volume and downloads the weights
offrig stage frontier --remove --yes         deletes the volume (the undo)
```

- ボリュームは、ポッドが実行されているかどうかにかかわらず、毎月請求されます（以前のバージョンの場合、300 GBは$0.07/GBで約$21/月）。そのため、ステージングを行うのは人間だけであり、エージェントツールはできません。
- ボリュームは1つのデータセンターに存在するため、プロファイルのポッドはその後、そのデータセンターでのみ起動され、オファーとプランはそのデータセンターで価格設定されます。ネットワークストレージとプロファイルのGPUを備えたものを選択してください。`offrig gpus`とRunPodのコンソールに、それらの場所が表示されます。
- ダウンロードは、そのデータセンターで利用可能な最も安価なGPUポッドで実行されます。ポッドは、成功時、失敗時、またはタイムアウト時に終了します。
- ボリュームは、ダウンロードが開始される前にプロファイルに記録されるため、ステージングが失敗した場合でも、それは決して忘れられません。再実行して再開するか、`--remove`を実行します。
- ステージングされた起動では、Hugging Faceはオフラインで実行され、ステージが完了したとき（ボリューム上のマーカー）にのみ実行されます。ステージングが不完全なボリュームは、失敗する代わりに残りをダウンロードします。

## 資金の安全性

- 起動前に、offrig は最も安い空きの候補と、ポッドを動かした場合の残り稼働時間（ランウェイ）を表示します。
  ランウェイが 1 時間未満なら、上書きしない限り起動を拒否します。残高がゼロになると、
  RunPod は offrig が管理していないものも含め、アカウント上のすべてのポッドを停止するためです。
- 自動停止は、すべての GPU の使用率が 5% 未満の状態が 30 分続くとポッドを終了します（設定変更可能、
  またはオフ）。
- ポッドが動いている状態でアプリを閉じると、終了するか動かし続けるかを確認します。
- offrig は自分で名前を付けたポッドだけを操作します。CLI とアプリでは `offrig-<profile>`、
  プロジェクトのサイドカーレーンでは `offrig-<tag>-<profile>` です（「レーン」を参照）。サイドカーは
  他のレーンのポッド、プレーンレーンのポッド、その他のポッドには決して触れません。それらは一覧に表示されるだけで、
  変更されることはありません。
- エージェントのセッションでは、支出の前に上限が適用されます。プランの最悪ケース（現在の
  価格 ×（最大時間 + 780 秒の自己停止テール）、セント単位で切り上げ）が人間の設定した予算に対してコミットされ、超える場合は拒否されます。
  起動はプラン ID だけを受け取るため、エージェントが自分で価格を決めることはできません。
- サイドカーの起動にはすべてウォッチドッグが付き、プランの期限にポッドを終了します。
  ランナーはキューが空になるとすぐにポッドを停止します。

## 脅威モデル

- **RunPod APIキー。** `RUNPOD_API_KEY`から読み取ります。ディスクやログには書き込まれません。Zed
プロバイダーは意図的に「`runpod`」という名前を避けています。なぜなら、そうしないと、Zedがそれを読み取ってしまうからです。
`RUNPOD_API_KEY` をモデルサーバーに送信します。
- **モデルサーバー。** SSHとお客様の秘密鍵でのみアクセス可能です。パスワードによるログインは無効になっています。
ポッド内では、sshdはローカルポートフォワーディングのみを許可します。
- **ホストキー。** 各エンドポイントごとに、別のknown_hostsファイルに固定して保存します。offrigはキーを忘れてしまうことがあります。
ポッドのエンドポイントが変更された場合にのみ、処理が行われます。なぜなら、RunPodはポッド間でIPアドレスとポート番号の組み合わせを再利用するからです。
- **シェルインジェクション。** モデル名が、Ollamaの命名規則に準拠しているかどうかが検証されます。
彼らは人里離れた場所にたどり着く。
- **孤立したトンネル。** オフリッグが死亡した場合、その`ssh`はポートを占有したままになることがあります。次の
「スタート・オフリグ」は効果を発揮するが、それは聴衆が「`ssh.exe`」を持ち、オフリグの正確なものを所持している場合に限る。
前方仕様に従います。それ以外のポートからのアクセスは拒否され、接続は確立されません。
- **テレメトリーは行いません。** offrigは、RunPodのAPI、お客様のポッド、およびローカルのOllamaとのみ通信します。
（モデルのリストを比較するため）。

### ランナーのリハーサル（2026年10月3日、小規模、RTX 2000 Ada、0.04ドルで予約済み）

5つのハンドオフがあり、そのうち1つは別のハンドオフに依存しており、誰も操作せずに`offrig_run`によって実行された。

- 4つのスロットで同時に4つのハンドオフ（16GBのVRAMのうち12.9GB）を実行。依存関係のあるハンドオフは、その依存関係が完了した瞬間に開始され、その結果に基づいて構築された。
- 受け入れチェックをカバーする3つのハンドオフは、それぞれ独立して完了した。競合するバックストーリー（部分的なチェック）と物語（チェックなし）は、レビューに回された。
- レビューは物語を返送した（「川の名前はプロジェクトに由来する」）。アクティブなランナーがそれを採用し、フィードバックに基づいて修正した（「ヴェイル川」）。
- キューは6.5分で処理された（6ターン、20,861トークン）。ランナーはポッドを自分でシャットダウンした。

判明したこと：決定的なチェックは、設計の品質ではなく、構造を検証します。4Bモデルは、曖昧な動詞を使用して「3つの動詞」に合格しました。したがって、`accept_on_checks`は構造的な作業用であり、設計作業はレビューに送られます。qwen3:4bは、3行の物語でも、ターンあたり約4,000トークンを費やしました。キューは、独立した引き継ぎが十分にある場合にのみ、すべてのスロットをビジー状態に保ちます。依存関係のあるチェーンは、一度に1つずつ実行されます。

## 標準への準拠

スタジオのワークフロー標準に基づいて評価（欠落：0、部分：1、存在：2、模範：3）。

- **PIN_PER_STEP：2。** ポッドイメージはバージョンタグに固定されています（`ollama/ollama:0.35.0`、`lmsysorg/sglang:v0.5.20-cu130`。レシピは`latest`を拒否します）、コンパイラは1.98.1に、依存関係は`Cargo.lock`で、Atlasエンジンはフリートの1.24.0に固定されています。各ハンドオフターンは、モデル、役割ハッシュ、およびプロンプトハッシュを記録します。モデルは、ダイジェストではなく、タグまたはリポジトリIDで固定されます。
- **ANDON_AUTHORITY：3。** すべてのステップで、欠陥が発生すると実行が停止します。ディスク容量を超える重みを持つプランは、費用が発生する前に拒否されます。失敗したプルは、起動を停止します。Zedの編集で読み戻しができない場合、書き込まれません。壊れた設定ファイルは報告され、再書き込みされることはありません。CIは、fmt、clippy、テスト、ライセンス、およびアドバイザリーでブロックされます。
- **NAMED_COMPENSATORS：2。** 変更不可のアクションにはすべて、以下のリストにあるように、元に戻す機能があります。
- **DECOMPOSE_BY_SECRETS：2。** 独自の理由で変更するものは、1つのモジュールにまとめます。RunPodのAPI（`runpod`）、ポッドの内容（`spec`）、トランスポート（`tunnel`、`remote`）、各ローカルファイルのオフリグ編集（`sshconfig`、`zed`）、およびルール（`guard`、`cost`）。フロントエンドは、プレゼンテーションを超えたロジックを持ちません。
- **UNCERTAINTY_GATED_HUMANS：2。** オフリグは、結果がコストがかかるか、または損失が発生する場合にのみ、必要な情報を尋ねます。1時間未満の実行時間で起動する場合、ポッドを終了する場合（失われるものが明記されている）、およびポッドがまだ課金されている状態で終了する場合。2つの決定は、人間だけが行うものであり、エージェントツールでそれを行うことはできません。予算の上限と、月額で課金されるボリュームのステージングです。コードでチェックできないハンドオフ出力は、完了する代わりにレビュー待ちになります。
- **EXTERNAL_VERIFIER：該当なし。** 特殊な主張はありません。
