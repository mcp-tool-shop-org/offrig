レンタルされた RunPod GPU で大規模モデルを実行し、以下の保証を提供します。モデルは、お客様自身の GPU 上で実行されることはありません。デスクトップアプリ、CLI、およびエージェント用の MCP サイドカーを、1 つの Rust ライブラリとして提供します。

サイドカーを使用すると、エージェントは、ユーザーが設定した予算内で有料セッションを計画し、GPU をレンタルし、役割に基づいてタスクのキューを独立したランナーに渡すことができます。ランナーは、すべてのモデルスロットを稼働状態に保ち、失敗したチェックに対してのみ修正を行い、キューが空になるとポッドを停止します。監視プログラムは、他のすべての処理が完了した場合でも、計画の期限までにポッドを終了します。

## ステータス

2026 年 10 月 2 日と 2026 年 10 月 3 日に実証され、合計約 5 ドルでした。

- **Frontier:** 4 × RTX PRO 6000 (384 GB) で、SGLang 上の Qwen3-Coder-480B (4 ビット AWQ) を実行。22 分で準備完了後、31 件のタスクを 20 秒で処理し、費用は 3.59 ドル。
- **Swarm データ:** 1 つのロードされたモデルで、一度に数百のエージェントにサービスを提供。480B は 512 エージェントで 4,059 トークン/秒を達成。1 つのカード上の 30B は、256 エージェントで 10,147 トークン/秒を達成。
- **Runner:** 依存関係と再処理キューを持つキュー。誰かが制御していなくても動作し、タスクが完了するとポッドが停止します。
- **保証:** ローカル GPU は、すべての実行中にアイドル状態を維持します。

2026 年 10 月 7 日から、2 つのプロジェクトで同時に毎日使用されており、それぞれが独自のワークフローで実行されています。aspire-si のトレーニングは `job` ポッドで、ai-jam-sessions のレンダリングは `jam` ポッドで行われます。

構築およびテスト済みで、決定を待っています。ネットワークボリュームに Frontier の重みを配置し、月額約 21 ドル（[Staging](#staging-weights-on-a-network-volume) を参照）。

次：最初の実際の Frontier キューを、起動前に完全に計画します。コードのハンドオフは、ポッド上でコンパイルおよびテストされます。

## 機能

1 つのウィンドウ（または 1 つのコマンド）から、offrig は次の処理を行います。

1. RunPod の残高、現在の GPU の価格、および残高がどのくらい持つかを表示します。
2. 1 つの小さなカード（Ollama）から、4 × RTX PRO 6000（SGLang）まで、ティアのポッドを起動し、そのモデルをポッドにロードします。
3. ポッドへの SSH トンネルを開きます。
4. ポッドのモデルを Zed に独自のプロバイダーとして追加します。
5. モデルがこのマシンで実行されないことを確認する 7 つのチェックを実行します。
6. ポッドを停止するか、すべての GPU がアイドル状態になった後、一定期間経過後にポッドを終了します。

サイドカーを通じて、エージェントは予算に基づいてセッションを計画し、圧縮と再起動間でプロジェクトのメモリを保持し、監視なしでハンドオフキューを実行することもできます（[The side-car](#the-side-car-for-agents) を参照）。

## 保証とその維持方法

- **モデルサーバーは、トンネル経由でのみアクセスできます。** ポッドは、ポッド自身のループバックにバインドされた、固定されたエンジン（Ollama (`ollama/ollama:0.35.0`) または SGLang (`lmsysorg/sglang:v0.5.20-cu130`)）を実行し、ポッドは `22/tcp` のみを公開します。見つけて悪用できるパブリック HTTP エンドポイントはありません。レシピは、エンジンをループバックから移動させることができません。
- **Zed は、独自のポートでトンネルと通信します。** トンネルは `127.0.0.1:11435` でリッスンします。ローカルの Ollama は `11434` にあります。offrig は、トンネルを `11434` に配置することを拒否するため、切断されたトンネルがローカルサーバーに到達することはありません。代わりに、リクエストは失敗します。
- **Zed は、プロバイダーを切り替えません。** ポッドのモデルは、Zed 内の別の `offrig` プロバイダーです。ポッドがダウンしている場合、それらのいずれかを選択するとエラーが発生します。Zed は、別のプロバイダーを試行しません。
- **重みはローカルに存在しません。** モデルは、ポッドによってポッド上にプルされ（または、Hugging Face からダウンロードされるか、ステージングされたネットワークボリュームから読み込まれます）。

ガードチェックは、offrig が観察できる事実に基づいて、毎回これを検証します。

| チェック | 失敗する場合 |
|---|---|
| トンネルがローカルの Ollama ポートを回避する | トンネルポートが 11434 である |
| Zed がトンネル経由でポッドモデルを送信する | Zed のプロバイダー URL がトンネル以外のものになっている |
| ポッドの Ollama がインターネットに公開されていない | ポッドがポート 11434 をパブリックにマッピングしている |
| トンネルがポッドで終了する | トンネル経由で読み取ったモデルリストが、SSH 経由でポッド上で読み取ったリストと異なる |
| ポッドモデルがこのマシンに存在しない | ポッドモデルがローカルの Ollama にも存在する |
| ポッドモデルとローカルの Zed モデルで名前が同じではない | offrig プロバイダーのいずれかの名前が、Zed のローカル Ollama リストにも含まれている |
| Zed が提供するすべてのモデルがポッド上にある | Zed がポッドに存在しないモデルを提供している |

## インストール

OpenSSH（組み込み）、Zed（モデルをエディターで使用する場合）、および RunPod アカウントを備えた Windows が必要です。

1. [Releases](https://github.com/mcp-tool-shop-org/offrig/releases) から `offrig-<version>-windows-x64.zip` をダウンロードし、リリースの `SHA256SUMS` と照合して、解凍して `PATH` に配置します。これには、`offrig.exe`（CLI）、`offrig-app.exe`（アプリ）、および `offrig-mcp.exe`（サイドカー）が含まれます。ソースからビルドする場合は、Rust 1.98.1（`rust-toolchain.toml` に固定）で `cargo build --release` を実行します。
2. RunPod API キーを、ユーザー環境変数 `RUNPOD_API_KEY` に配置します。
3. SSH パブリックキーを、RunPod のアカウント設定に追加します。offrig は、存在する場合は `~/.ssh/runpod_rustline`、次に `~/.ssh/id_ed25519` を使用します。
4. エージェントの場合、サイドカーをユーザーのスコープで Claude Code に登録します。`claude mcp add --scope user offrig -- <path>\offrig-mcp.exe`。これは、プロジェクトが初めて使用するときにのみプロジェクトのストアを開くため、使用しないプロジェクトでは無害です。

[handbook](https://mcp-tool-shop-org.github.io/offrig/handbook/) では、最初のポッド、サイドカー、構成、ワークフロー、およびジョブポッドについて説明します。

## 使用方法

**アプリ:** `offrig-app` を起動し、プロファイルを選択し、**Launch pod** を押します。準備ができたら、モデルが Zed のエージェントパネルに「RunPod · …」として表示されます。最初の起動後、Zed を 1 回再起動すると、`OFFRIG_API_KEY` が表示されます。

**CLI:**

```text
offrig status                 balance, runway, pods
offrig gpus --count 2         live offers for a GPU count
offrig profiles               tiers and their models
offrig up medium              launch, pull, wire Zed, run the checks, hold the tunnel
offrig up frontier --wait 180  wait up to 3 hours for the GPUs, renting nothing meanwhile
offrig tunnel medium          hold the tunnel to a running pod
offrig check gpt-oss:120b     streamed chat with a tool call, the way Zed sends it
offrig guard                  run the seven checks
offrig pull <model>           pull another model onto the pod
offrig connect                open the pod's /workspace in Zed for remote editing
offrig down medium --yes      terminate the pod
offrig zed-remove             take the provider out of Zed
offrig budget 15              set this project's spending cap for agent sessions (human only)
offrig stage frontier --dc EUR-IS-1 --yes   stage weights on a network volume (bills monthly)
```

### 出力、終了コード、およびエラー

- **ログレベル:** `-q` はエラーとコマンド自身の結果のみを出力します。`-v` は、各 RunPod 呼び出しとその実行時間を追加します。`--debug` は、失敗したレスポンスの本文と完全なエラーチェーンを追加します。API キーは、すべてのレベルで削除されます。
- **終了コード:** `0` は成功、`1` は修正が必要な問題（引数、設定、ガードまたは予算の拒否、キーの欠落）、`2` は実行時のエラー（RunPod、ネットワーク、ssh、タイムアウト、空き容量なし）を示します。
- **サイドカーエラー**は結果であり、プロトコルエラーではありません。`ok:false` は安定した `code`、`error` のテキスト、`next_action`、および `retryable` を含みます。コードは、[ハンドブックのリファレンス](https://mcp-tool-shop-org.github.io/offrig/handbook/reference/)にリストされています。

## サイドカー（エージェント用）

`offrig-mcp` は、Claude Code などのエージェントが使用する MCP サーバーです。各プロジェクトに対して `<project>/.offrig/offrig.db` にデータベースを保持し、すべてのポッドよりも長く存続するため、セッションは圧縮または再起動後も、情報を再説明することなく維持されます。

| ツール | 機能 |
|---|---|
| `offrig_status` | プロジェクト、予算、RunPod の残高と利用可能時間、offrig のポッド、各オープンプランとその `plan_id`、レーン、ポッド名、保留中の作業がフラグ付けされたハンドオフキュー。 |
| `offrig_offers` | GPU の数に対するライブ GPU オファー |
| `offrig_plan` | セッションの最悪のケース（ライブ価格 x 最大時間）で価格を設定します。予算を超えた場合は拒否されます。レスポンスには、レーンの `ssh_alias` と、起動時に作成される `pod_name`、および要求される `container_disk_gb` が含まれます（オプションの `container_disk_gb` はプロファイルのものをオーバーライドします。詳細は「コンテナディスク」を参照）。オプションの `max_price_hr` と `no_fallback` は、レンタルできる GPU を絞り込みます（「プランのハードウェアを固定する」を参照）。オプションの `wait_minutes` は、空き容量がない場合に起動が再試行する回数を設定します（「空き容量を待つ」を参照）。 |
| `offrig_memory_search` | アクティブなプロジェクトメモリを検索し、各結果にはソースと日付が含まれます。 |
| `offrig_memory_record` | 簡単な説明、制約、決定、事実、またはチェックポイントを追加します。変更は、理由とともに以前のものを置き換えます。 |
| `offrig_handoffs` | 役割に基づいてハンドオフをキューに入れ（それぞれに受け入れチェックが必要です。オプションの決定的なチェック）、リスト表示し、役割ブロックのプレビューを表示し、ハンドオフの最適な出力を表示します（これも `.offrig/out/` に書き込まれます）。結果を記録します（完了、無効、違反、失敗、フィードバックによる再試行）。 |
| `offrig_launch` | **実行します。** `plan_id` のみを受け入れます。最悪のケースをコミットし、GPU をレンタルせずに待機し、ポッドを起動し、トンネルを開き、モデルをプルし、監視プログラムを開始します。プランごとにべき等です。レーンにすでにライブプランまたはポッドがある場合は拒否されます。`lane <tag> has a live pod <name> (plan <id>); shut it down first` |
| `offrig_job` | 起動の進行状況（ポッドが起動している間、ステップは呼び出しの瞬間のポッドの状態から派生します。各空き容量の再試行は `progress.capacity_wait` でカウントされます）、実際にレンタルされた GPU の種類とホストの CUDA バージョン（ポッドで `nvidia-smi` を使用して測定し、ホストがプランの CUDA 最小値よりも古い場合は、大きな `warnings` エントリを表示します）、監視プログラムの稼働状況、残りの時間、これまでの実行時間。 |
| `offrig_ask` | ポッドモデルでのハンドオフの 1 ターン、コンテキストはプロジェクトストアから構築されます。レスポンスは、信頼できない出力として返されます。 |
| `offrig_run` | すべてのモデルスロットを稼働状態に保つ分離されたランナーを開始します。各準備完了のハンドオフをドラフトし、失敗したチェックに対して最大 2 回修正し、結果を依存するハンドオフに供給し、キューが空になるとポッドをシャットダウンします（ただし、`keep_pod` の場合を除く）。コードでチェックできない作業は、レビュー待ちとして保留されます。 |
| `offrig_put` | ローカルファイルまたはディレクトリをジョブポッドにコピーします（scp）。相対ポッドパスは `/workspace/job` の下にあります。オプションの `plan_id`（以下を参照）。 |
| `offrig_exec` | ジョブポッドで bash コマンドを実行し、サイドカーよりも長く存続するように分離します（`start`）。実行中または終了したコマンドの終了コードとログの末尾（`status`。`save_log` は、ログ全体をローカルファイルにもコピーします）を報告します。コマンドを終了します（`stop`）、または短いコマンドを今すぐ実行し、stdout、stderr、および終了コードを返します（`run`、`timeout_secs` のデフォルトは 30、最大 120）。オプションの `plan_id`（以下を参照）。 |
| `offrig_get` | ジョブポッドからファイルまたはディレクトリをコピーし、不足しているローカルの親フォルダーを作成します。ポッドのディスクを削除するシャットダウンの前に実行します。オプションの `plan_id`（以下を参照）。 |
| `offrig_shutdown` | **ポッドを破棄します。** ポッドを終了し、測定された実行時間でプランの会計を閉じます。ハンドオフが進行中の場合は、理由が与えられない限り拒否されます。レーンがそのポッドの名前を付けた場合、レーンの独自の `~/.ssh/config` ブロックを削除します（`ssh_block_removed`）。 |

**ジョブツールが作用するジョブプラン。** `offrig_put`、`offrig_exec`、および `offrig_get` は、オプションの `plan_id` を受け入れます。オープンしているジョブプランが 1 つだけで、`plan_id` がない場合、以前と同様にそれを使用します。オープンしているジョブプランが複数あり、`plan_id` がない場合、拒否し、オープンしているプラン（ID、プロファイル、ポッド名）をリスト表示します。推測はしません。`plan_id` がある場合、そのプランのポッドに対してのみ作用し、ポッドの名前がそのプランが所有するものであることを確認した後でのみ作用します（別のレーンのポッドは拒否され、別のレーンであるというだけでは拒否されません）。すべてのジョブツールのレスポンスと `offrig_job` には、作用した `project` と `plan_id` が含まれます（ジョブツールのレスポンスには `lane` も含まれます）。`offrig_status` には、`project` が含まれ、各オープンプランとその `plan_id`、レーン、およびポッド名がリスト表示されます。

役割は、Role OS（ドキュメントとスターターパックカード）と、Role OS の形式でここに同梱されている 4 つのゲーム役割（ゲームデザイナー、システムデザイナー、ナラティブデザイナー、ロアキーパー）から取得されます。予算の上限は、人間が設定します。

```text
offrig budget 15          set this project's cap (run in the project directory)
offrig budget             show cap, committed, spent, remaining
```

すべての起動は、**監視プログラム**を開始します。これは、エージェント、セッション、またはサイドカーがなくなった場合でも、プランの期限（コミットされた時間 + 最大時間）にポッドを終了する別のプロセスです。失敗した検索に対しては作用せず、正確に 1 回終了し、会計を閉じ、`.offrig/watchdog-<plan>.log` にログを記録します。レンタルされたポッドの準備が失敗した場合、起動はポッドを終了し、課金されたまま放置することはありません。

設計とその証拠は、[docs/sidecar-design.md](docs/sidecar-design.md) にあります。

### レーン：プロジェクトごとに 1 つのサイドカー、競合はありません

2 つのプロジェクトは、1 つの RunPod アカウントで同時にサイドカーを実行できます。各プロジェクトには、他のプロジェクトが共有しない独自の **レーン**（SSH エリアス、トンネルポート、ポッド名タグ）が割り当てられます。

| | プレーンなレーン（CLI、アプリ、Zed） | プロジェクトのレーン |
|---|---|---|
| SSH エリアス | `offrig` | `offrig-<tag>` |
| トンネルポート | `11435`（ランナー `11436`） | 最初の空き `11500`、`11502`、...（ランナー：上記のポート） |
| サイドカーポート（シェルドライバー） | なし | `11700` + レーンのスロット：`11700`、`11701`、... |
| ポッド名 | `offrig-<profile>` | `offrig-<tag>-<profile>` |
| SSHブロック | `# >>> offrig:offrig >>>` | `# >>> offrig:offrig-<tag> >>>` |

`<tag>`は、プロジェクトフォルダーの名前（`aspire-si`、`ai-jam-sessions`）から取得され、2つのプロジェクトが同じフォルダー名を使用する場合に短いハッシュが追加されます。プロジェクトのレーンは、最初にセッションを計画するときに割り当てられ、offrigの構成ディレクトリにある`lanes.toml`に書き込まれ、保持されます。同じプロジェクトには、再起動後も常に同じレーンが割り当てられます。割り当てにはロックファイルが使用され、レジストリがアトミックに書き込まれるため、同時に起動する2つのサイドカーは、タグ、エイリアス、またはポートを共有することはありません。どのレーンも`11434`（ローカルOllamaのポート）にすることはできません。範囲は`11500`から始まり、それ以外を指定するように編集されたレジストリは拒否されます。プランは、自身のレーンを記録し、起動、ランナー、監視、シャットダウンはすべてそのレーンを使用し、グローバル構成は使用しません。

サイドカーは、常に自身のレーンに名前が付けられたポッドとのみ一致、リスト、または停止します。別のプロジェクトのレーン、プレーンレーンの`offrig-<profile>`ポッド、およびアカウント上のその他のポッドはそのままにします。ライブポッドの起動チェックは、自身のレーンのみを対象とし、シャットダウンは、プランのレーンではない名前のポッドを拒否し、トンネルの孤立チェックは、転送とエイリアスがレーンのものでない場合にのみ、古い`ssh`を停止します。レーンが存在する前に作成されたプランは、レーンを記録しておらず、プレーンレーンで実行され続けるため、古いスキームで起動されたポッドは、それを起動したのと同じプランによってシャットダウンされます。

**サイドカー自身のポート。** `offrig-mcp`は、stdio経由でMCPと通信します。セッション全体にわたって1つを開いたままにするシェルドライバー（セッション自身のMCP接続が不安定な場合）は、それをループバックHTTPポートの背後に配置し、そのポートは以前はマシン全体で1つの番号でした（`11439`）。別のプロジェクトのドライバー、またはその他のプログラムがそれを取得すると、最初のサイドカーは何も言わずに停止していました。現在は、プロジェクトごとにデフォルト設定されており、トンネルポートと同様に、プロジェクトのレーンから取得されます。レーンスロット`i`（トンネルポート`11500 + 2i`）には、サイドカーポート`11700 + i`が割り当てられます。範囲`11700`から`11763`は、レーンが持つことができるすべてのトンネルポートとランナーポート（`11500`から`11627`）、プレーンレーンの`11435`と`11436`、およびローカルOllamaの`11434`よりも上にあります。したがって、サイドカーポートはトンネルポートになることはありません。新しいものは保存されません。`lanes.toml`は変更されず、ポートはレーンから派生します。`OFFRIG_SIDECAR_PORT`は引き続きそれをオーバーライドします。ポートではない値、1024未満の値、または`11434`、`11435`、`11436`、またはレーントンネル範囲内の値は拒否されます。

```
offrig-mcp --sidecar-port --project <dir>           # print the port; allocates the lane if the project has none
offrig-mcp --sidecar-port --check --project <dir>   # also exit 1 if something already holds it
```

`--check`を使用すると、使用中のポートはエラーとなり、ポートの名前と、そこにoffrigサイドカーが応答する場合に、それが提供するプロジェクトの名前が表示されます。「サイドカーポート11700は使用中です。offrigサイドカーがすでにそこでプロジェクト<path>を提供しています。最初にそれを停止するか、OFFRIG_SIDECAR_PORTを空いているポートに設定してください」。このチェックは、ドライバーがすでに応答する方法（誰も提供していないプロジェクトとしてリクエストし、ドライバーはツールに触れる前にそれを拒否します）と同じであるため、実行中のサイドカーには何も変更が加えられません。`offrig_status`は、レーンの`sidecar_port`を報告します。

**1 レーンにつき稼働中のポッドは 1 つ。** レーンには SSH エイリアスとトンネルポートが 1 つずつしかないため、同時に扱えるポッドは 1 つです。同じレーンに 2 つ目のポッド（`offrig-<tag>-jam` の隣の `offrig-<tag>-job`）があると、エイリアスがそちらを指すようになり、最初のプランの `offrig_put`、`offrig_exec`、`offrig_get` が別のマシンに送られてしまいます。そのため `offrig_launch` は、レーンに開いているプランや稼働中の自分のポッドがある間は、何かを確定・レンタルする前に `lane <tag> has a live pod <name> (plan <id>); shut it down first` というメッセージで拒否します。プレーンレーンの `offrig up` とアプリも、別のプロファイルのポッドに対して同じように拒否します（同じプロファイルのポッドは引き続き再利用されます）。最初のプランをシャットダウンしてから、次を起動してください。

`recipe`を持つプロファイルは、Ollamaとは異なるエンジンを実行します。ピン留めされたイメージ（`lmsysorg/sglang:v0.5.20-cu130`）、起動時にダウンロードするHugging Faceモデル、および追加のサーバー引数です。offrigは、GPU数からテンソル並列処理、プロファイルからコンテキスト長を設定し、エンジンをポッドのループバックに保持します。レシピはそれらをオーバーライドできません。ゲートされたリポジトリの場合、`hf_token_secret`はRunPodシークレットの名前を指定し、`{{ RUNPOD_SECRET_<name> }}`として参照されるため、トークンはポッド仕様に入ることがありません。起動は、エンジンの`/health`とモデルリストを待ち、ダウンロード中にディスク上の重みを報告し、エンジンが終了した場合はすぐに停止します（エンジンのログ付き）。

各プロファイルは、優先順位の順にGPUタイプをリストします。RunPodは、容量のある最初のGPUを選択します。空きがない場合、プロファイルは待機できます（`wait_for_gpu_minutes`。最先端は最大120分待ちます）。offrigは1分ごとにチェックし、GPUが解放された瞬間にポッドを作成します。待機中は何もレンタルされません。Ctrl+Cまたはアプリのキャンセル起動で停止し、RunPodの価格APIがダウンしている場合は、1分ごとに作成を再試行します。大規模なマルチGPUセットアップは、数分で開始および停止します。価格はセキュアクラウド価格であり、リアルタイムで読み取られます。価格ページは、利用可能な価格ではありません。

### 容量を待機中

プランが `no_fallback` または `max_price_hr` で絞り込まれると、多くの場合、必要なリソースが不足するため、ジョブは失敗する代わりに静かに再試行し、実行中に何もレンタルしません。再試行までの待機時間は、次の順序で決定されます。まず、プランの `wait_minutes`（プランに保存されている `offrig_plan` 引数。`0` は即座に失敗します）。次に、プロファイルの `wait_for_gpu_minutes`。 `job` プロファイルでは、デフォルトで 20 分に設定されます。待機時間は、プランの残り時間から 5 分間の余裕を引いた時間に短縮されるため、プランの期限を過ぎることはなく、待機中に何もレンタルされないため、最悪の場合のコストに影響はありません。 `offrig_launch` は `capacity_wait_minutes` を報告します。待機中は、 `offrig_job` に `progress.capacity_wait`（`checks`、`waited_secs`、`limit_secs`）と、現在のチェックがどれであるかを示すステップが表示されます。待機時間が終了すると、ジョブは `no capacity` で失敗し、何もレンタルされません。

### プランのハードウェアを固定する

プロファイルは、GPU の種類を優先順位の順にリストし、RunPod は利用可能な最初の GPU を選択します。制限がない場合、プランは、メモリが少なく、古いドライバーが搭載され、価格が異なるバックアップ GPU に割り当てられる可能性があります。3 つの制限により、プランは、実際に使用できるハードウェアに制限されます。プランの作成は引き続き無料ですが、制限は、プランがレンタルできるものを絞り込むだけです。

| 制限 | 場所 | 効果 |
|---|---|---|
| `min_cuda` | プロファイル（`config.toml`） | RunPod のリストにある最も古いホスト CUDA（ドライバー）バージョン（`13.0`、`12.9`、... `11.8`）。ポッドの作成時に、このバージョン以上のすべてのバージョンが `allowedCudaVersions` として送信されます。ジョブプロファイルの場合、このバージョンとイメージ自体の `[profiles.job] min_cuda` のうち、新しい方が適用されます。 |
| `min_vram_gb` | プロファイル | プランが受け入れることができる、プロファイル内のすべての GPU の合計 VRAM の最小値。この値以下のオファーは破棄され、RunPod がメモリ情報をリストに持っていないタイプも破棄されます。 |
| `max_price_hr` | `offrig_plan` 引数 | ポッドの総コストの最大値（すべての GPU の合計 $/時間。 `offrig_offers` に表示される数値）。この値を超えるオファーは破棄され、現在価格がリストにないタイプも破棄されます（上限に準拠することはできません）。 |
| `no_fallback` | `offrig_plan` 引数 | プロファイルの最初の GPU ファミリーのみが許可されます。2 つの RTX PRO 6000 Blackwell エディション（Server と Workstation）は 1 つのファミリーであり、それ以外のすべてのカード（A100 SXM および PCIe を含む）は、それぞれ独自のファミリーです。 |

両方のプロファイルフィールドはオプションであり、デフォルトでは設定されていません。したがって、以前の offrig によって記述された `config.toml` は、変更せずにロードされます。 `job` プロファイルは `min_cuda = "13.0"` を設定します。

`offrig_plan` は、残っているものから最悪の場合のコストを計算します。
`max_hours x min(max_price_hr, the dearest listed price among the remaining GPUs)`。制限がない場合、
`max_price_hr` は、以前と同様に、プロファイルにリストされている最も高価な価格になります。何も残っていないプランは、破棄された各 GPU の理由とともに拒否され、何も書き込まれません。

プランは、残っている GPU のリストと CUDA の下限を保存し、`offrig_launch` はそれらからのみレンタルし、プロファイルの完全なリストからはレンタルしません。 `offrig_job` とサイドカーのジョブ結果は、実際にレンタルされた GPU のタイプとホストの CUDA バージョンを `rented` オブジェクトで報告します。ポッド API はホストの CUDA バージョンを報告しないため、ssh が確立されると、ジョブは `nvidia-smi` を 1 回実行し、ヘッダーから読み取ります（`CUDA Version: 12.8`、または新しいドライバーの場合は `CUDA UMD Version: 13.4`）。 `rented.cuda_source` は `nvidia-smi` または `pod API` を示します。ホストの CUDA がプランの下限よりも古い場合、GPU がプランにリストされていない場合、または価格がプランの上限を超える場合、`offrig_job` は `warnings` エントリを返し、`next_action` を `WARNING` で開始します。自動的に終了されることはありません。レンタルの停止は、呼び出し元の責任です（`offrig_shutdown`）。ポッド API または `nvidia-smi` のいずれからも CUDA バージョンが提供されない場合、`rented.notes` はその旨を通知し、下限はチェックされません。

### コンテナディスク

ポッドには、ホストにローカルなコンテナディスクと、`/workspace` にマウントされるボリュームという 2 つのディスクがあります。一部のホストでは、`/workspace` は速度の遅いネットワークファイルシステムです。あるジョブポッドでは、そこで 32 MB/s、コンテナディスクでは 354 MB/s と測定され、約 130 GB のモデルを時間内に取得できませんでしたが、コンテナディスクはわずか 60 GB でした。コンテナディスクのサイズは、プロファイルの `container_disk_gb`（組み込みプロファイルでは 30 ～ 60 GB、`job` プロファイルでは 60 GB）であり、ポッドの作成時に `containerDiskInGb` として送信されます。 `offrig_plan` は `container_disk_gb`（1 ～ 2000）を受け取り、1 つのプランに対してこれを上書きします。プランはそれを保存し、ジョブはそれを送信し、プランの応答と `offrig_status` は、実際に使用されるサイズを表示します。

- コンテナディスクは**価格に含まれません**。offrig が価格に含めるのは GPU 時間だけなので、プランの最悪ケースはサイズにかかわらず同じです。RunPod はディスクにも課金します。RunPod がポッドについて報告するレート（`offrig_job` に表示）にコンテナディスクが含まれるかどうかは、ここでは確認していません。
- offrig はダウンロード先を移動しません。ジョブのコマンドは `/workspace` ボリューム上の `HF_HOME`（`/workspace/hf`）で始まります。コンテナディスクを使うには、コマンドで自分で設定してください（`HF_HOME=/root/hf python ...`）。
- コンテナディスクは、ネットワークボリュームのないボリュームと同様に、ポッドとともに削除されます。`offrig_shutdown` の前に `offrig_get` で結果をコピーして戻してください。
- 1〜2000 の範囲は、入力ミスに対する offrig 独自の妥当性チェックです。RunPod の実際の上限は確認していません。

### ジョブポッド

`job` を持つプロファイルは、トレーニングジョブなどの、GPU で実行される作業のために GPU をレンタルします。モデルの提供のためではありません。そのポッドは、ピン留めされた PyTorch イメージ（`runpod/pytorch:2.8.0-py3.11-cuda12.8.1-cudnn-devel-ubuntu22.04`、Blackwell の CUDA 12.8）を実行し、sshd とそれ以外は何も実行しません。

- モデルを提供しないため、トンネルはなく、Zed にも何も接続されません。sshd はフォワーディングを一切許可しません（`AllowTcpForwarding=no`）。入る方法はポッドへの ssh だけです。
- ジョブプロファイルはモデルを列挙せず、レシピも持てません。設定チェックはどちらも拒否します。
- `offrig up` とアプリは、何もレンタルする前にジョブプロファイルを拒否します。ジョブプロファイルはサイドカー経由で実行します：`offrig_plan profile=job`、`offrig_launch`、その後 `offrig_put`、`offrig_exec`、`offrig_get`。sshd が応答した時点で起動完了です。
- コマンドはポッド上の `/workspace/job` でデタッチして実行されます（`setsid nohup`）。そのため、サイドカーや ssh セッションが終了しても動き続けます。コマンドは base64 で送られるので、ssh シェルがその中身を読むことはありません。ログと終了ステータスは `/workspace/offrig/jobs/` に残ります。Hugging Face のダウンロードはポッドボリュームの `/workspace/hf` に保存されます。
- `offrig_exec action=run` は作業ではなく簡単な確認（`ls`、`nvidia-smi`）のためのものです。コマンドを `timeout`（既定 30 秒、最大 120 秒）のもとで最後まで実行し、`stdout`、`stderr`、`exit_code`、`timed_out` を返します。出力は各ストリームの最後の 64 KB に切り詰められ（`truncated`）、信頼できないポッド出力として扱われます。より長くかかるコマンドは `start` を使います。
- ジョブのログ末尾では進捗バーがまとめられます。キャリッジリターンでつながった tqdm 形式の再描画は、最後のフレームだけが表示されます。`offrig_exec action=status save_log=<ローカルパス>` は、ジョブのログ全体を書かれたとおりローカルファイルにコピーします（親フォルダーは作成されます）。そのため末尾は短いままで済みます。
- イメージは CUDA 12.8 ビルドなので、ジョブプロファイルは動作する最も古いホスト CUDA バージョン（`min_cuda = "12.8"`）を指定し、ポッドはそこから RunPod の `allowedCudaVersions` を使って作成されます。これがないと、古いドライバーのホストでポッドが起動し、レンタルが始まった後で torch が GPU を見つけられなくなります。作業そのものがイメージ以上を必要とすることもあります。`job` プロファイルは、実行するジョブが CUDA 13 ビルドの PyTorch を使う最新の vLLM をインストールするため、プロファイルにも `min_cuda = "13.0"` を設定しています（上記参照）。
- 予算、プラン、ウォッチドッグ、シャットダウンは他のプロファイルと同じように動作します。`offrig_shutdown` の前に結果をコピーして戻してください。ポッドのディスクはポッドとともに失われます。
- `jam` は ai-jam-sessions が歌声のレンダリングに使うジョブプロファイルです。SoulX-Singer はトレーニング用カードよりはるかに少ないリソースで動くため、安価な 24〜48 GB のカードをレンタルします。セットアップとセッションはそのリポジトリ（`docs/vocal-offrig.md`）にあり、offrig は歌については何も知りません。

### ネットワークボリュームへの重みのステージング

レシピプロファイルは、起動時に毎回重みをダウンロードします。以前のバージョンでは、準備完了までに約20〜22分かかりました（252GB、$8.36/時間）。ステージングでは、重みをRunPodネットワークボリュームに一度だけ配置します。

```text
offrig stage frontier --dc EUR-IS-1          shows the monthly cost, changes nothing
offrig stage frontier --dc EUR-IS-1 --yes    creates the volume and downloads the weights
offrig stage frontier --remove --yes         deletes the volume (the undo)
```

- ボリュームは、ポッドが実行されているかどうかにかかわらず、毎月課金されます（以前のバージョンの300GBは約$21/月、$0.07/GB）。したがって、ステージングを行うのは人間だけであり、エージェントツールはできません。
- ボリュームは1つのデータセンターに存在するため、プロファイルのポッドはその後、そこでのみ起動し、オファーとプランはその場所で価格設定されます。ネットワークストレージとプロファイルのGPUを備えたものを選択してください。`offrig gpus`とRunPodのコンソールには、それらの場所が表示されます。
- ダウンロードは、そのデータセンターで利用可能な最も安価なGPUポッドで実行されます。ポッドは、成功時、失敗時、またはタイムアウト時に終了します。
- ボリュームは、ダウンロードが開始される前にプロファイルに記録されるため、ステージングが失敗した場合でも、それは決して忘れられません。再実行して再開するか、`--remove`を使用します。
- ステージングされた起動では、Hugging Faceはオフラインで実行され、ステージが完了したとき（ボリューム上のマーカー）にのみ実行されます。半ステージングされたボリュームは、失敗する代わりに残りの部分をダウンロードします。

## 資金の安全性

- 起動前に、offrigは最も安価な空きリソースと、ポッドが実行されている場合の残りのリソースを表示します。1時間未満のリソースが残っている場合、オーバーライドしない限り拒否します。残量がゼロになると、RunPodはアカウント内のすべてのポッド（offrigが管理していないものを含む）を停止します。
- 自動停止は、すべてのGPUの使用率が5%未満になった30分後にポッドを終了します（設定可能、またはオフにできます）。
- ポッドが実行されている状態でアプリケーションを閉じると、それを終了するか、実行し続けるかを尋ねられます。
- offrigは、名前を付けたポッドにのみアクセスします。CLIとアプリケーションの場合は`offrig-<profile>`、プロジェクトのサイドカーレーン（「レーン」を参照）の場合は`offrig-<tag>-<profile>`です。サイドカーは、他のレーンのポッド、プレーンレーンのポッド、またはその他のポッドには決してアクセスしません。それらはリストに表示されるだけで、変更されることはありません。
- エージェントセッションの場合、上限は支出前に適用されます。プランの最悪のケース（現在の価格×最大時間）は、人間が設定した予算に対してコミットされ、それを超えると拒否されます。また、起動にはプランIDのみが必要なため、エージェントは独自の価格を設定できません。
- すべてのサイドカー起動には、プランの期限までにポッドを終了する監視機能があり、ランナーはキューが空になるとすぐにポッドをシャットダウンします。

## 脅威モデル

- **RunPod API キー。** `RUNPOD_API_KEY` から読み取り、ディスクやログには一切書き込みません。Zed のプロバイダー名をあえて `runpod` にしていないのは、その名前だと Zed が `RUNPOD_API_KEY` を読み取り、モデルサーバーに送ってしまうためです。
- **モデルサーバー。** あなたの鍵を使った SSH 経由でのみ到達できます。ポッドではパスワードログインが無効で、sshd はローカルフォワーディングのみを許可します。
- **ホスト鍵。** エンドポイントごとに、専用の known-hosts ファイルに固定されます。RunPod はポッド間で ip:port の組を再利用するため、offrig が鍵を忘れるのはポッドのエンドポイントが変わったときだけです。
- **シェルインジェクション。** モデル名は、リモートシェルに渡る前に Ollama の名前構文で検証されます。
- **孤立したトンネル。** offrig が異常終了すると、その `ssh` がポートを保持し続けることがあります。次回起動時に offrig はそれを終了させますが、リスナーが offrig の正確なフォワード指定を持つ `ssh.exe` である場合に限ります。ポート上のそれ以外のものは拒否され、決して終了させません。
- **テレメトリなし。** offrig が通信するのは RunPod の API、あなたのポッド、そしてローカルの Ollama（モデル一覧の比較のため）だけです。

`scripts/verify.sh`（または`scripts/verify.ps1`）は、フォーマットチェック、clippy、テスト、および各バイナリの簡単な実行を1つのコマンドで実行する。CIはまた、`cargo deny`（OSVスキャン）、`Cargo.lock`へのカバレッジ、および`atlas check`も実行する。

### ライブテスト記録（2026年10月2日、ミディアムティア、A100 80GB、約0.45ドル）

- ポッドの起動には約80秒かかり、sshd、トンネル、およびポッドのOllama 0.35.0が応答する。
- ポッドに約150〜250MB/sの速度で97GBのモデルがダウンロードされる。
- `qwen3-coder:30b-a3b-q8_0`と`gpt-oss:120b`はそれぞれ、トンネル経由で正しいツール呼び出しを含むストリーミングチャットに応答した。これらは、ポッドのVRAMの36GBと64GBを消費した。ローカルのOllamaは何もロードされず、ローカルGPUにも存在しなかった。
- CLIとアプリケーションの両方から、7つのガードチェックすべてがパスした。
- 突然終了したCLIは、その`ssh`がポートを占有したままになり、次の実行でポートが再利用された。
- アプリケーションのトンネル、チェック、モデルテスト、およびシャットダウンは、ボタンを通じて実行された。

ライブ実行で発見され、修正され、テストされたバグ：バックグラウンドで実行された`&&`リストがsshのstdoutを開いたままにし、プル開始を停止した。ポッドリストにGPUタイプが不足していた（`includeMachine=true`がない場合）。起動チェックで、実行中のポッドの価格が2回カウントされた。

### サイドカーリハーサル（2026年10月3日、スモールティア、RTX 2000 Ada、0.08ドル予約）

インストールされた`offrig-mcp`が、エージェントが呼び出す方法であるstdio経由で実行される。

- `offrig_plan`は、最悪の場合で0.5時間を0.15ドルと見積もり、`offrig_launch`がそれをコミットし、ウォッチドッグを開始し、2回目の呼び出しで同じジョブが返された。1つのポッドが0.24ドル/時間でレンタルされた。
- レンタル後100秒でSSHが起動し、`qwen3:4b`がプルされ、150秒で準備完了。
- `offrig_ask`は、46秒でゲームデザイナーの引き継ぎを実行した。応答は、その受け入れチェックを満たし、メモリから5つの箇条書きの制約を維持した。
- ポッドはインターネットにアクセスした（Wikipedia、GitHub API）。ポッドが取得したデータに基づいて、モデルは現在の質問に正しく回答した。質問された場合、ライブアクセスがないと答えた。
- `offrig_shutdown`は、新しいサイドカープロセスからポッドを終了し、処理を終了した。ウォッチドッグは、計画が終了したことを検出し、終了した。ローカルGPUは、全体を通してアイドル状態を維持した。

発見され、修正された：ポッドは一度に1つのリクエストを処理した（`OLLAMA_NUM_PARALLEL=1`）。4つのスロットで8つの並列リクエストを同じGPUから40〜102トークン/秒で処理できるように、各プロファイルに`parallel = 4`が追加された。理由なしに`complete`が拒否された（現在は「受け入れチェックが満たされた」がデフォルトになっている）。失敗には、依然として理由が必要である。ステータスは、セッションがアクティブな間に短い記録を記録することを示唆している。リプライに漏洩するテキストは削除され、思考によってリプライが空になった場合は、`max_tokens`を発生させる。

### ランナーリハーサル（2026年10月3日、スモールティア、RTX 2000 Ada、0.04ドル予約）

5つの引き継ぎがあり、そのうちの1つは別の引き継ぎに依存しており、誰かが駆動することなく、`offrig_run`によって実行された。

- 4つのスロットで同時に4つの引き継ぎが実行された（16GBのVRAMのうち12.9GB）。依存関係のある引き継ぎは、依存関係が完了した瞬間に開始され、その結果に基づいて構築された。
- 受け入れチェックをカバーする3つの引き継ぎは、それ自体で完了した。ライバルのバックストーリー（部分的なチェック）と、物語（チェックなし）は、レビューに送られた。
- レビューは、物語を返した（「川はプロジェクトにちなんで名付けられている」）。ライブランナーはそれを採用し、フィードバックに基づいて修正した（「ヴェイル川」）。
- キューは6.5分（6ターン、20,861トークン）で処理され、ランナーはポッド自体をシャットダウンした。

判明したこと：決定的なチェックは、設計品質ではなく、構造を検証する。4Bモデルは、あいまいな動詞を使用して「3つの動詞」に合格したため、`accept_on_checks`は構造的な作業に使用され、設計作業はレビューに送られる。qwen3:4bは、3行の物語でも、ターンあたり約4,000トークンを考えていた。キューは、独立した引き継ぎが十分にある場合にのみ、すべてのスロットをビジー状態に保つ。依存関係のあるチェーンは、一度に1つずつ実行される。

## 標準への準拠

スタジオのワークフロー標準に基づいて評価（0件の不備、1件の部分的な準拠、2件の準拠、3件の模範的な準拠）。

- **PIN_PER_STEP: 2.** ポッドイメージはバージョンタグに固定される（`ollama/ollama:0.35.0`、`lmsysorg/sglang:v0.5.20-cu130`；レシピは`latest`を拒否する）、コンパイラは1.98.1に、依存関係は`Cargo.lock`で、Atlasエンジンはフリートの1.24.0に固定される。各ハンドオフターンは、そのモデル、役割ハッシュ、およびプロンプトハッシュを記録する。モデルは、ダイジェストではなく、タグまたはリポジトリIDで固定される。
- **ANDON_AUTHORITY: 3.** すべてのステップで、欠陥が発生すると実行が停止する：ディスク容量を超える重みを持つプランは、費用が発生する前に拒否される。失敗したプルは、起動を停止する。Zedによる編集で、読み戻しができない場合は、書き込まれない。破損した設定ファイルは報告され、再書き込みは行われない。CIは、fmt、clippy、テスト、ライセンス、およびアドバイザリーでブロックされる。
- **NAMED_COMPENSATORS: 2.** 変更不可の操作には、それぞれ以下のとおり、元に戻すための手段がある。
- **DECOMPOSE_BY_SECRETS: 2.** 変更の理由に応じて、1つのモジュールに1つの機能を集約する：RunPodのAPI（`runpod`）、ポッドの内容（`spec`）、トランスポート（`tunnel`、`remote`）、各ローカルファイルのoffrigによる編集（`sshconfig`、`zed`）、およびルール（`guard`、`cost`）。フロントエンドは、プレゼンテーション以外のロジックを持たない。
- **UNCERTAINTY_GATED_HUMANS: 2.** offrigは、結果がコストがかかるか、または損失が発生する場合にのみ、確認を求める：1時間未満の実行時間で起動する場合、ポッドを終了する場合（失われるものを明示）、およびポッドが課金され続けている状態で終了する場合。2つの決定は、人間のみが行うことができ、エージェントツールでそれらを行うことはできない：予算の上限と、月額で課金されるボリュームのステージング。コードで確認できないハンドオフ出力は、完了する代わりにレビュー待ちとなる。
- **EXTERNAL_VERIFIER: n/a.** 特殊な主張はない。
